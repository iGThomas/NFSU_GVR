NFSU_GVR_Portable - NFS Underground: GlobalVR as a normal Windows game

Installs into a user-chosen folder with the GVR folders nested inside it:
  <ROOT>\Underground\  +  <ROOT>\Underground\GVR\{GvrRoot,GvrPlus,Gvr}

Version 2026-10-05-portable-v2-privreg.

Relocatable because the game learns its locations from its registry keys (Ini,
PlusSchemaPath x2, PublicKeyPath, GVRCrashMonitor Prog0x path), and GVRInputRaw.dll now
answers those from <ROOT>\nfsu_registry.ini (a private registry, created on first start,
folder values computed from the install every time) - nothing is written to the Windows
registry. UniverShell2.exe's hardcoded C:\gvrRoot strings are dead
editor constants (proven via Ghidra: zero xrefs); and the SQLite provider derives
game.db from the registry PlusSchemaPath so it needs no env var. No MSDE / SQL Server
/ SQLXML, no cabinet-lockdown Run keys, no fixed C:\, no system32 dependency
(runtime DLLs + patched engine + provider are placed app-local beside the EXEs).

Provider is compiled on the target with the machine's .NET 1.1 csc (prebuilt binary
is the fallback). Disc-based (asks for OEM Disc 1 / Disc 2) or -ExpandedPayloadRoot.

Diagnostics: set [Debug] Log=true in gvr_settings.ini and a LOG folder appears in the
install root (no reboot, no admin; off by default). It collects gvrlaunch.log (a PC
config dump - CPU, motherboard, GPU + driver version, OS build, RAM, display - then the
launch timeline), gvrinput-<exe>-<pid>.log (our input DLL in BOTH programs, with a native
crash filter recording the faulting module+offset) and gvrsqlite-<exe>.log (every DB query
plus any .NET crash in the frontend). Together they cover the frontend (UniverShell2) and
the race (UndergroundGVR). In the SQLite log, grep for 'prepare FAIL': untranslated T-SQL
fails at prepare time and silently returns zero rows with no in-game error. The legacy env
vars (GVRSQLITE_LOG / GVRINPUT_LOG / GVRLAUNCH_VERBOSE) still force logging on.

Win10/11 (x64): real
.NET 1.1 SP1 installed via slipstream (plain dotnetfx = MSI 1603, and CLR 2.0
redirection AVs inside PLUSDE's native C++ EH); app-local DXVK d3d9.dll caps the
framerate-tied physics at 60fps (game side only); cabinet GammaSet.exe disabled
(its rundll32 NvCpl.dll call pops a RunDLL error on 64-bit Windows).

Everything configurable lives in gvr_settings.ini and is applied AT LAUNCH by
GvrLaunch.exe / GVRInputRaw.dll / GvrCardKey.exe - resolution, fullscreen or
borderless window, and the full controller map for both programs. Neither EXE
has a settings screen, so those constants are patched in memory on every start;
no executable on disk is ever modified. Start the game with GvrLaunch.exe.
Use a 4:3 mode: the engine never adapts its projection to the render aspect,
so 16:9 stretches the image (the installer picks the largest 4:3 that fits).

Fonts: Disc 1 ships a Fonts component with four families no Windows has (GVR_nfsu,
GVR_digital, Ethnocentric, Digital dream Narrow) that the shell's art.gvr asks for by
name; without them the main menu, circuit name and operator menu fall back to Arial.
The installer registers ONLY the missing families with Windows - the one thing it puts
outside the install folder - and keeps copies in <InstallRoot>\Fonts. Loading them
app-locally with AddFontResourceEx(FR_PRIVATE) was tried and renders those fields as
unreadable garbage, with or without FR_NOT_ENUM.

Free play: the shipped game.db sets Settings_NFS1.FreePlay = 1 deliberately. The stock
cabinet value is 0 (an operator wants the coin door to charge); a home install has no
coin mechanism or dongle, so with it off the frontend asks for credits it can never
receive. It is the only value changed from the stock settings row, and it remains a
normal operator setting - press O in the frontend to switch it back off.
